# C1 前端工程与产品气质

> 草稿 · 2026-09-11

默认做简单、易用、克制、精确的产品。用户打开界面就能看清当前内容、真实状态和下一步动作；长时间使用仍然舒适。视觉品质来自排版、对齐、层级和反馈的准确性。

这份 Skill 同时约定工程底座和默认 taste。技术底座承载可靠交互，情绪板决定颜色、字体、密度和形状，页面结构由用户任务决定。

## 使用边界

- 用户对当前任务的明确要求优先，其次是项目已确认的产品说明、设计系统和组件约定，再使用本 Skill 的默认值。外部参考用于补充判断。
- 新项目采用下述技术架构和情绪板。已有项目先检查框架、token 和组件；局部修改沿用现状，不因加载 Skill 自动迁移技术栈或重做品牌。
- 默认气质主要服务于操作型与阅读型产品界面。营销、作品展示和品牌活动页面按任务调整构图与表达，不自动套用工作台密度；真实性、可访问性和交互完整性要求仍然适用。
- 用户已给出清楚的方向就直接落实。只有缺失信息会实质改变页面任务、品牌或行为时才澄清。

## 前端工程默认值

| 层级       | 默认选择                             | 职责                                    |
| ---------- | ------------------------------------ | --------------------------------------- |
| 应用       | React + TypeScript + Vite            | 组件、类型、开发与构建                  |
| 样式       | Tailwind CSS 4 + `@tailwindcss/vite` | 布局、响应式、状态样式和语义 token 映射 |
| 基础组件   | shadcn/ui 的 **Base UI 版本**        | 项目拥有源码，集中维护外观、尺寸和变体  |
| 交互原语   | `@base-ui/react`                     | 复杂控件的组合、键盘与焦点行为          |
| 变体与图标 | CVA、`cn`、Lucide React              | 一致的变体、类名组合与线性图标          |
| 产品表达   | 语义 CSS 变量、Geist / Geist Mono    | 配色、字体、密度、圆角和层次            |

版本按项目兼容性和锁文件确定。shadcn 提供组件源码，Base UI 提供底层交互，它们都不替代产品设计。简单控件可以使用原生元素。

先复用现有组件，再增加必要的 variant。共享外观进入基础组件，页面组合留在业务组件，业务状态与请求规则保持独立。

新增项目、组件或主题时阅读 [架构与维护边界](references/architecture.md)。

## 默认感觉与外观

**克制、清醒、可信、专注、连续。**

- **矿物白与石墨色。** 略带绿灰的中性色形成安静的层次，石墨色承担主操作；深浅主题保持相同的语义关系。
- **颜色解释意义。** 蓝色提示信息与焦点，绿色表示已确认的成功，琥珀色提示阻塞或风险，红色表示失败或危险。普通待办保持中性；普通选中、业务完成和保存成功各自有清楚的含义。
- **控件紧凑，正文舒展。** Geist 承担日常阅读，Mono 只用于代码、时间戳和精确标识；文字角色、行长和中文排版保持一致。
- **连续的内容表面。** 先用共同边界、留白和细分隔组织内容。容器用于输入、交互分组和浮层，避免把每段内容都装进卡片。
- **有角色差异的几何。** 普通控件、组合输入区和浮层采用各自的圆角尺度。常规内容保持平面，阴影只在需要区分浮层时使用。
- **默认静止。** 动效解释变化、保持连续性；庆祝或展示性动画按产品任务决定，减少动态效果时，内容和操作依然完整。

实施视觉前阅读 [配色情绪板与排版](references/mood-board.md)，默认设计取值以该文件为准；本节只作摘要，架构代码只示意映射。项目采用后，以项目已确认的主题与组件为准，不随个人 Skill 更新自动改版。新品牌可以改变表达，但仍需保持语义、可读性和一致性。

## 任务与内容组织

先确认谁会在什么情境下打开页面、要完成什么，以及哪些状态、证据或限制会改变他的下一步。按用户需要组织内容，不按原始材料的顺序或页面类别套模板。

| 当前任务 | 首屏重点与组织方式 |
| --- | --- |
| 查找与操作 | 工作对象、当前状态和主要动作直接可见；列表与详情按查找路径连接 |
| 比较与判断 | 把备选项放在相同基准上，让差异能直接看见；结论有对应证据 |
| 趋势与异常 | 突出时间关系、变化或例外，保留精确记录的查阅入口 |
| 计算与试算 | 输入、核心结果和必要假设组成一个可操作区域，用户可立即调整变量 |
| 阅读报告与详情 | 用标题、关键值和说明支持快速理解，用明细、方法与来源支持深入核验 |

首屏呈现当前任务的核心对象或动作。没有证据支持结论时，呈现已知状态、限制或待解决问题，不编造推荐。营销与展示页面围绕其真实传播目标构图，不套用上表中的工作区布局。

每个分区回答一个新问题；同一结论有一个主要呈现位置，明细表可以保留精确查找，但摘要、图表和卡片不反复重复同一个答案。报告与详情的核验资料靠近相关结论或按需展开，操作界面则优先保证工作路径。页面结束处交代实际结果、可执行的下一步或尚未解决的问题。

## 事实与表达

- 保留事实、公式、单位、对象范围、时间、比较条件与不确定性，区分观察、推导、预测、建议和因果判断。缺少依据时明确未知，不虚构数值、归属、期限、审批或完成状态。
- 简化语言时保留改变含义的限定条件，用具体事实代替“极快”“安全”等无依据评价。标题表达用户的问题、发生的变化或需要的决定；陌生术语先解释，再一致使用。
- 让读者能核验实际方法和限制，不把“如何设计此页面”等制作过程写进产品文案。资料不充分时保留真实空缺，不用装饰、指标卡或虚假精度补足内容。

## 设计判断

1. **先组织关系，再选择组件。** 根据对象、操作与证据的关系安排布局。存在真实结构分岔时，比较不同的内容位置、密度和阅读路径，选择更容易完成任务的方案；不能只换配色就当作不同设计。
2. **层级来自关系。** 同级内容采用一致的排版和基线；相关内容靠近，段落转折留出更大间距。每个间距只有一个所有者。
3. **熟悉的交互建立信任。** 导航、表单、Tabs 和弹窗采用成熟模式。组件有一致的外观，也有完整的焦点、错误和等待反馈。
4. **真实状态比漂亮状态更重要。** 未保存、执行结束和业务完成不能混为一谈。失败保留用户输入，并说明可做的下一步。
5. **适配不同屏幕。** 窄屏下调整布局，保留主要内容和操作入口。切换视图或主题时，保留用户输入、选中项和阅读位置。

每个主要区域有清楚的重点，辅助内容降低权重。页面缺少重点时，先调整比例、分组、顺序和留白；只有实际同级的内容才使用等权重网格，不能为了整齐把重要程度不同的内容都装成相同卡片。

区分内容过多与视觉过强：前者通过删减重复、合并或重排解决，后者通过减少竞争的颜色、字号、字重、边界和动效解决，同时保留主要对象的辨识度。卡片套卡片、重复摘要和装饰性图表用于诊断信息价值；Hero、badge、渐变、媒体和编辑表达按具体任务判断。

编写或修改控件时阅读 [组件规范](references/components.md)。

## 工作方式

1. **看现状。** 读相关产品说明、token、现有组件和当前页面。明确用户的主任务、主要动作和需要保持的状态。
2. **定表达。** 复用已确认的情绪板；没有品牌要求时使用本 Skill 默认值。先安排内容层级、组件关系和窄屏组织，再调整局部外观。
3. **做相关状态。** 按组件需要覆盖 default、hover、focus、pressed、disabled、pending，以及页面的 loading、empty、error、success。保存与冲突等状态只在实际业务涉及时补齐。
4. **检查真实组合。** 运行相关的类型、构建和行为检查。在浏览器先缩略查看首屏，确认主对象和阅读路径清楚；再看全页分组、基线、意外空白与重复信息。用真实长内容检查桌面、窄屏、相关主题、语义与标题层级、键盘路径和焦点；主题变化核对 portal 中的浮层。
5. **说明结果。** 简短说明改动、实际验证与尚未验证的边界。截图证明外观；真实保存、执行和恢复需要对应业务链路证据。

不要用通用检查表代替用户要求的交付。对局部修改按影响验证；对新页面验证主要使用路径。先修影响理解或操作的问题，在修复后复查受影响部分，按任务验收结束，不为追求额外风格变化反复重做。
